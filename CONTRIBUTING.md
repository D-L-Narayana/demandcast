# Contributing to DemandCast

Thanks for helping to make store-level forecasting and replenishment a little more transparent.
This project is deliberately small and dependency-light; most contributions are a model, a
query, a CLI option or a test. The notes below keep the repository consistent.

## Set-up

```bash
git clone https://github.com/D-L-Narayana/demandcast && cd demandcast
python -m venv .venv            # any Python >= 3.10; activate it with your shell's activate script
pip install -e ".[dev]"         # numpy + pytest, ruff, mypy
make check                      # ruff check + ruff format --check + mypy + pytest
```

`make` targets use `$(PYTHON)` (default `python3`); point it at another interpreter with
`make PYTHON=path/to/python check`.

### Optional local pre-commit hook

The repository does not ship a pre-commit configuration. If you like ruff to run on every
commit, create `.pre-commit-config.yaml` locally with this content, then `pip install pre-commit`
and `pre-commit install`:

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.10
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format
```

It mirrors `make lint`; CI remains the source of truth.

## Ground rules

* **Runtime dependencies stay NumPy only.** `demandcast/` imports the standard library and
  `numpy`, nothing else (`tests/test_compat.py` enforces it). Dev tooling may grow in the
  `dev` extra.
* **Python 3.10 compatible.** CI runs 3.10, 3.12, 3.13 and 3.14. No `tomllib`, `typing.Self`,
  `datetime.UTC`, `StrEnum`, `except*`, PEP 695 generics. Pass ISO strings (not `date` objects)
  to sqlite3.
* **Schema changes are additive** and go through `db.migrate()` (new nullable/defaulted columns,
  tables, indexes); bump `SCHEMA_VERSION` and add a migration test. Existing query names and
  their output columns are stable; columns may be added.
* **The default synthetic dataset is frozen.** New generator features must draw their random
  numbers after the existing draws or be opt-in; the hash test in `tests/test_simulate.py` will
  tell you.
* **The dashboard is one self-contained HTML file with zero JavaScript** and must satisfy the
  content-security policy in [docs/deployment.md](docs/deployment.md); run
  `python scripts/verify_dashboard.py --html out/index.html` after touching `dashboard.py`.
* **Portable public files.** Everything under version control uses relative paths; no
  machine-specific paths, virtualenv paths, session identifiers or tool/author attribution
  lines in code, docs, CI or benchmarks (`tests/test_compat.py` scans for them). The dashboard
  footer stays "Generated by DemandCast".

## Test-first

Write the test before the behaviour:

1. Add a failing test that states the contract (an assertion failure, not an import error).
2. Implement the smallest change that makes it pass.
3. Keep tests deterministic (seeded RNGs), fast (the whole suite runs in seconds; use tiny
   datasets such as 2-3 stores x 4-8 products x 200-300 days and `workers=1`) and isolated
   (write only under `tmp_path`; never write `dashboard/index.html` from a test).
4. Never delete, rename or loosen an existing test; extend it or add a new one. Marking tests
   `skip`/`xfail` to get green is not acceptable.

Useful commands:

```bash
python -m pytest -q -rs                       # whole suite
python -m pytest tests/test_models.py -q      # one file
python -m ruff check . && python -m ruff format --check .
python -m mypy demandcast                     # also run in CI with the scripts
make smoke                                    # the CI end-to-end CLI sequence
make demo                                     # backdated run + evaluation on fresh data
python benchmarks/bench.py --quick            # timings (never commit the output)
```

## Style

* ruff (line length 100, rules `E, F, I, B, UP, SIM, C4, PT, RUF`) and ruff-format decide
  formatting; mypy with `check_untyped_defs` must stay clean for `demandcast/`.
* Type hints on all public functions; docstrings carry the equations where maths lives (see
  `replenish.py`, `models.py`).
* SQL: one `-- name:` block per query with a comment that explains the technique, SQLite
  named parameters (`:run_id`).
* Keep the teaching style: prefer a readable formula over a clever one-liner.

## Pull requests

* One topic per PR; include the test(s) and, for user-visible changes, the docs
  (`docs/cli.md`, `docs/methodology.md`, `docs/architecture.md`, `README.md`) and a CHANGELOG
  entry.
* Report measured numbers (timings, accuracy) together with the machine they came from; the
  README figures are re-measured by the maintainer before a release.
* CI must be green on every Python version in the matrix.

The maintainer owns releases, the version number and the deployment of the live dashboard.
